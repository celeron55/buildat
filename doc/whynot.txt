Decisions against, and why
==========================
Things that were considered and not done, so the question is not reopened
by accident. The plan's own "not this" notes are beside the items they
belong to.

Why not use protobuf?
- It would suck for modules because it has many moving parts

Why not detect -DURHO3D_64BIT automatically in the build system?
- It's not possible

Why not use cereal's versioning system?
- It doesn't support forward compatibility

Why not allow making arbitrary number of instances of any module?
- It would make module reloading and management practically impossible, and it
  would make module interoperability much harder to achieve. Creating a robust
  but usable system for threading is also tricky. Also, it does not make that
  much sense to run multiple worlds in a single server process because then all
  would crash if one crashes.
- Instead there should be easy mechanisms for launching new server processes at
  runtime, and routing clients to different processes.

Luanti features left out on purpose, not to be added
-----------------------------------------------------
Official Luanti's client has these; buildat's two Luanti clients do
not, and the decision (user, 2026-09-22) is that they stay out. A
game that needs one is a game that needs official.

- Cinematic mode (F8, the smoothed camera).
- Pitch move (the fly mode that follows the pitch).
- Autoforward (the toggled forward key).
- Block bounds (the mapblock outline overlay).
- New profiler features of any kind: the engine's own DebugHud on F6
  is the whole of it.


The launcher room's discarded pieces, not to be rebuilt
-------------------------------------------------------
Taken out of `extensions/launch_world` on purpose (user, 2026-09-24 and
2026-09-25). Each was built, looked at, and decided against.

- The loading reel: two chrome hubs with a spoke across each, turning
  while a bay came apart. A discarded idea rather than a thing waiting
  for its turn. The dissolve is the piece worth reusing -- a bay
  un-builds into a flying cube per voxel, reversible and interruptible
  with no keyframes -- and it belongs to activation, which `launch()`
  is the one door for.
- Opening a bay by hand: Return on a pointed orb opened its pocket and
  Backspace closed it. It was unreachable from either mode, and a
  player who wants a pocket open wants what is in it launched -- the
  bay opening is the launch's own animation.
- The room's own key for leaving a game (F10). A game leaves through
  `buildat.leave()`, and the launcher does not rig anything up to make
  games behave.


The server's box: what it is not built on
-----------------------------------------
Decided 2026-10-02 and 2026-10-03 ([PROCESS_SANDBOX]).

- bubblewrap bundled with the archive. Ubuntu 23.10 and later refuse
  unprivileged user namespaces to a program without an AppArmor profile,
  so a copy at our own path fails exactly where it would matter. The
  system's bwrap may be an extra layer; Landlock and seccomp are the box.
- The Windows box's local client bridged through loopback. Loopback is
  blocked between an AppContainer and the rest of the machine both ways
  (the user's probe runs), and a bridge inside the box would need loopback
  there too; the client joins by a named pipe in the container's
  namespace, a second transport for the same byte stream.
- Low integrity on Windows instead of an AppContainer: it does not
  restrict reading, and reading the user's files is half of what the box
  is for.

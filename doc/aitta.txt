Aitta packages: an app packed, signed and installed
===================================================
A release is two files, the archive
and its signature; it is installed from them, from the command line or
from an Aitta registry through the client.

The manifest
------------
An app's meta.json, at the app directory's root (apps/<app>/meta.json):

    {
        "author": "celeron55",        a-z, 0-9 and _, 1 to 40
        "name": "digger",             the same
        "version": "1.0.0",           letters, digits, . - + _, 1 to 40
        "engine_api": 1,              the engine API its C++ is written for
        "license_code": "Apache-2.0",
        "license_media": "CC-BY-SA-4.0",
        "description": "Dig down.",   300 characters at most
        "home_hearth": "https://forum.buildat.org",   optional: where
                                      its feedback and news go
        "changelog": "CHANGELOG.md",  optional: a file in the archive
        "kind": "app",                optional: "app" or "extension"
        "audience": "everyone"        optional: "everyone", "teen" or
                                      "adult"; Aitta's page at / lists
                                      only "everyone" and "teen"
    }

A package of kind "extension" is a client extension: init.lua at its
root, run in the client's sandbox like extensions/ (an app's client Lua
requires it, or a launch_ui.txt beside it makes it a launch UI, always
sandboxed). The client names it "<author>__<name>", so neither part may
have "__" in it or start or end with _. It has no saves to pin, so an
installed version replaces the one before it. An author/name stays the
kind it was first installed as.

engine_api is interface::aitta::ENGINE_API (src/interface/aitta.h), which
the engine bumps when a change breaks modules. A release that asks for
more than the running engine has is not packed or installed.

The commands
------------
    bin/buildat aitta keygen <key file>
        A new author key. Prints its public half. The file is the secret:
        whoever has it publishes as you. It is never overwritten.

    bin/buildat aitta pack <app dir> <key file> <out dir>
        Writes <author>-<name>-<version>.zip, the app directory (names
        starting with '.' left out), and .sig beside it: the zip's
        sha256, the public key and its signature over the hash.

    bin/buildat aitta install <release .zip> <user path>
        Checks the hash, the signature and the manifest, and unpacks into
        <user>/installed/<author>/<name>/<version>/. The first version
        installed keeps its key in <user>/installed/<author>/<name>/key; a
        later version signed by another key is refused. A version already
        there is not replaced: an update is a new directory beside it.

    bin/buildat aitta install <Aitta> <author>/<name>[@<version>] <user path>
        The same, fetched from an Aitta's list by name: the version asked,
        else the newest listed. A version not listed is refused with the
        versions there are; one installed already is only said. Prints the
        version's directory.

    bin/buildat aitta publish <release .zip> <Aitta's host:port>
        Uploads a release to an Aitta (apps/aitta). Its key has to be bound
        to its author name there first.

Publishing from the client
--------------------------
Settings, Developer, "Publish an app or extension" (not on the web
client) does the commands above without a terminal:
  - Packages are directories in <user>/dev_apps/<name>; "New app..." and
    "New extension..." write a small one there (an app with client Lua
    only), and "Open folder" opens it. A dev app is a "Dev" tile on the
    launch grid ("dev:<name>"; its server and saves know it as <name>);
    a dev extension is loaded over an installed one of the same name.
  - The manifest form edits meta.json, each field checked as it is typed,
    the reason under it.
  - "Create my publishing key" writes <user>/aitta_keys/<author>.key.
    "Bind on <Aitta>..." joins the Aitta with the author name and public
    key filled in its Bind form (the Aitta's account signs in there);
    "Back to the launcher" returns. The screen asks the Aitta's
    GET /api/aitta/info?key=<public key> ({ok, licences, author}) whether
    the key is bound.
  - "Pack and publish" packs into <user>/aitta_releases and uploads. A
    version already published is refused with "Raise the version", which
    raises the last number of the version and saves it; "Pack and
    publish" again publishes that.
util/aitta_publish_check.sh drives all of it.

Aitta, the registry
-------------------
apps/aitta is a buildat app. An author joins it (its accounts: a local
account, or a Starport ID where its admin set that up), and binds an
author name to the public key keygen printed; the name and the key do
not change after. A published release is checked -- the signature by a
bound key, the hash, the manifest, its author being the key's, the
licences against the instance's list (free ones by default, in its
settings), the size -- and listed, unreviewed. The admin can delist.
A package's later release is listed once it is the settings'
"update_delay" seconds old (0 by default), so a release made with a
stolen key can be reported and delisted before clients are offered it.
The page at / is for a browser that may be anyone's: it lists a release
only once it is "page_delay" seconds old (3600 by default), and only one
whose audience is "everyone" or "teen". The admin changes a setting
with the app's request {"cmd": "set_settings", "settings": {...}}.

The server's moderators and admins are its reviewers: "Review releases"
on Aitta's page lists the releases to review, oldest first; a release's
page has its meta, its files (each viewable as text), a diff against the
package's last reviewed release, a checklist, and Reviewed, Needs
changes (the note to the author), Relabel (the audience; the author
cannot set it back without a review) and Delist, each in the audit log
with whether the reviewer playtested it. Playtest makes a ticket (an
hour, one fetch of each file, a release not listed too) and leaves to
the launcher, which asks in its own dialog before it installs the release
under <user>/review/<author>__<name>/<version>, apart from the installed
ones, and starts it: to its server "review.<author>__<name>", saves of
its own. Its tile is badged Playtest, with a "remove" tile beside it.

Anyone reports a release: "Report..." on Aitta's page in the launcher or
on an installed tile, or the form on a package's web page. The reasons
are Starport's and malware, licence and broken. A report weighs the
setting "anon_weight" (0.01) without a key and "key_weight" (0.1) with
the client's report key, more or less by the key's record; one network
counts once in a group (a release and a reason). Past the "thresholds"
({hide, delist} by reason; malware and CSAM 1 and 2) a release is out of
the list until a moderator looks. "Reports" on Aitta's page is the
moderators' queue: dismiss, or unreview, delist the release, delist the
package or bar the author from publishing (days, or until lifted). The
author reads what was done on their Aitta page ("What was done to my
releases") and appeals there; another moderator than the one who acted
decides. A delisted release installed in a client is noted on its tile
when the launcher next fetches that Aitta's list.

    GET  /api/aitta/list                      the listed releases, JSON, and
                                              the delisted ones with why
    POST /api/aitta/report                    {release, reason, text, key}
    POST /api/aitta/report_status             {key, receipts}: outcomes
    GET  /api/aitta/archive/<sha256>.zip|.sig a listed release's files
    GET  /api/aitta/info?key=<public key>     {ok, licences, author}: the
                                              author the key is bound to
    GET  /                                    a page of each package's latest
                                              release, for a browser
    GET  /p/<author>/<name>                   a package's listed releases

The web client of an Aitta server is at /app (/play and /index.html
work too).

Browsing and installing in the client
-------------------------------------
"Apps from Aitta" on the launch grid lists the Aittas in the Starport
settings (https://aitta.buildat.org by default; the managed file's
"aittas", or "aitta" for one, overrides them), merged, a package a row
with its newest release ([AITTA_PAGE_LAYOUT], laid out as Browse): the
search filters as it is typed, the dropdown by state (All, Installed,
Updates, Not installed), Ctrl+S sorts by name or newest. The selected
package's panel has its version, kind, author, review state, licences,
size, description and changelog, and Install, or Update where another
version of it is installed, Discuss and Report...; Enter or a second
click on its row installs. Escape closes the page. The client fetches
the release and its .sig and checks them itself before installing; the
new version is on the grid at once. Where the
Starport filters hide unreviewed content ("Apps from Aitta (unreviewed)",
under the lock, or the managed file's filters.unreviewed), a package
shows only its newest reviewed release, and one with none is not shown.

Running an installed app
------------------------
Every installed version is a tile on the launch grid, "<label> <version>",
and starts a sandboxed server from its directory. To the client it is
"<author>.<name>@<version>"; to its server, and to its save, shared and
cache directories, "<author>.<name>": every version is one app. `buildat -a
installed/<author>.<name>@<version>/<id>` runs its tile on boot.

A save remembers the release that made it (version and sha256, from the
.aitta_sha256 the install leaves in the version's directory), and another
version of the app does not open it. Where two versions of an app are
installed, each has a second tile, "<label> <version>: move saves here",
which plays that version and moves the saves another version made to it
(the launch parameter aitta_move_saves=1).

On a dedicated server [AITTA_SERVE]
-----------------------------------
util/serve_latest_release.sh takes <author>/<name> as a game: it runs the
newest version installed in that server's user directory, as the server
<author>.<name> (its saves under <user>/apps/<author>.<name>/). Install it
first with the command above, or set AITTA=<the Aitta's address>: then
the script installs it, and at each update check installs the newest
listed release, compiles it and restarts onto it as it does for a new
engine release (the same wait for players, the same warning). Without
AITTA the installed version stays until one is installed by hand. A
package's page on the Aitta shows these commands with its name filled in.

    AITTA=https://aitta.example util/serve_latest_release.sh someone/lamps 29500 ~/lamps-user

The key is ECDSA P-256 (Mbed TLS, in the tree); signing is deterministic
(RFC 6979), so a release packed twice is the same .sig. util/aitta_check.sh,
util/aitta_pin_check.sh, util/aitta_serve_check.sh and apps/aitta/check.sh are the checks.

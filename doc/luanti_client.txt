Luanti client
=============
extensions/luanti_client makes buildat_client talk to an unmodified Luanti
server: it does the client's side of Luanti's protocol.

    $ bin/buildat_client -m luanti_client

It asks for an address, a player name and a password, logs in, and shows the
terrain around the player. BUILDAT_LUANTI_ADDRESS sets the address the dialog
starts with, which is what scripted runs (-c) use. Escape disconnects.

Every node but air is drawn as one placeholder cube for now; what a node
really looks like needs the node definitions and the server's media.

The network dialog of extension/network asks about the address the first time;
see doc/client_api.txt.

What is where
-------------
serialize.lua   Luanti's big-endian numbers and length-prefixed strings
connection.lua  The UDP transport: channels, reliable packets, acks, splits
srp.lua         The client half of the SRP-6a login, on buildat.bignum
client.lua      The commands: the login, the map blocks, and dispatch for the
                rest
world.lua       The scene: a node per map block, with buildat's voxel mesher
                on it
engine_test.lua Checks of the engine primitives, run at boot
init.lua        The connect dialog and the status screen

The engine side of this is nothing Luanti-specific: sockets (extension/network),
SHA-256 and bignum arithmetic (buildat.sha256, buildat.bignum).

Checks
------
    $ lua extensions/luanti_client/test.lua

covers serialize.lua and connection.lua against a fake socket: the packet
framing, numbers including f32, reliable packets arriving out of order or
twice, acknowledgements, resending, splitting what is sent and reassembling
what arrives, and the peer id handshake.

    $ bin/buildat_client -m luanti_client

runs engine_test.lua at boot, which checks the engine primitives the extension
leans on: buildat.compress / buildat.decompress and
buildat.pack_voxel_volume.

srp.lua has self_test(), which init.lua runs at boot; its vectors come from
util/srp_reference.py, which does SRP-6a separately in Python.

Both login paths have been run against a real Luanti server: registering a new
player (FIRST_SRP) and logging in as one the server knows (SRP), and the
terrain of that server's world has been on screen.

How the world sits: a buildat voxel and a Luanti node both occupy the cube
centred on their integer coordinate, so Luanti node coordinates are Urho3D
world coordinates one for one. A map block is 16^3 nodes and the mesher wants a
one-voxel border to cull faces against, so a block goes in as an 18^3 volume:
itself plus a slice off each of the six neighbours that have arrived. A
neighbour arriving makes the block's mesh out of date; until it does, there is
a seam. Packing a block's volume and handing it to the mesher costs the frame
about 350 us on a 2013 workstation; the meshing itself is on a worker thread.

What is done
------------
- The UDP transport, both directions, splits included
- Registering and logging in, and the peer id and protocol version handshake
- INIT2, and access denied messages
- CLIENT_READY once ITEMDEF and NODEDEF have arrived, which is what makes the
  server spawn the player, and then PLAYERPOS every 0.1 s
- Map blocks: BLOCKDATA at serialization version 29, acknowledged with
  GOTBLOCKS, which is what keeps the server sending more
- MOVE_PLAYER (where the server put us) and TIME_OF_DAY
- The terrain on screen: a scene node per map block, meshed by buildat's voxel
  mesher, dropped again once it is far enough away

Only serialization version 29 is read. It is what every current server writes;
older ones compress the pieces of a mapblock separately and the client says so
and gives up rather than carrying a second parser.
